# l10n — design

A cross-language localisation library: **verified C#/TypeScript conformance, on-device (no API call), tree-shakable, typed.** Personal open-source (destined). Builds on `f8n` (identity/money) and is generated by `c5n` (shared codegen). See `../f8n/DESIGN.md`, `../c5n/DESIGN.md`.

## North star (every decision serves these)
1. **Verified cross-language conformance** — C# and TS produce identical output, **verified against a comprehensive shared fixture set** (not "provably identical for all inputs" — the guarantee is exactly the fixtures' coverage; see Formatting model).
2. **On-device, no API** — formatting logic + locale data baked into the libs; no network round-trip, no runtime service, no failure mode.
3. **Tree-shakable** — ship only the locales and messages you actually use; no fat bundle.
4. **Typed** — message access is strongly typed; wrong or missing params are compile errors.

## The gap it fills
Existing i18n is one of: API/runtime-based (drift-prone, network-dependent), a fat on-device bundle, or no cross-language guarantee at all. This gives all three at once — which ≈ doesn't exist.

## Settled by adjacency
Much of the original agenda is fixed by decisions in `f8n`/`c5n`:
- **Source of truth → YAML**, en-GB authoritative (dev contact point), **namespaced per scope** (shared / team / UI chrome / per-app).
- **Codegen → `c5n`** (the shared Go engine) — `l10n` feeds it templates + schema; it does *not* build its own generator.
- **Locale identity → `f8n`** (`Locale`: parse / canonicalise / match). `l10n` builds *presentation* on it; identity is not `l10n`'s (putting identity here is the tempting mistake: matching and canonicalisation have no presentation concern).
- **Formatting data → CLDR** — patterns, plural rules, display names; **derived from source and baked** (kills the OS/version/runtime-ICU drift).
- **Conformance → the golden-vector / fixtures hub** from `c5n` — one language-neutral fixtures file, each target must produce identical output per input.
- **Money/Currency/Percentage** formatted here consume `f8n`'s types (presentation lives in `l10n`, the types in `f8n`).

## Formatting model — conformance by *verification*
The crux (l10n's analog of f8n's money-arithmetic problem): **identical formatting across C# and TS, on-device, without trusting platform ICU** (`CultureInfo`/`Intl` wrap ICU, which drifts by version/OS). The approach is **conformance-by-verification, not by-construction:**

- **Derive locale data from CLDR and store it** — this pins the *biggest* variable (the data), independent of the runtime's bundled ICU.
- **Format using the language's own features, *directed by* that stored data** — don't reimplement ICU's engines.
- **Fixtures keep it honest** — the shared fixtures file is read by each target; identical output per input is the test. Where platforms diverge, fix (special-case or own that bit).

**Asymmetry to design around — JS is the awkward side.** .NET's formatters *accept* injected locale data (`NumberFormatInfo` separators/patterns, `DateTimeFormatInfo`), so C# can be "directed from source". But **`Intl.NumberFormat`/`Intl.DateTimeFormat` accept only structured *options*** (fraction digits, `style`, `useGrouping`, `signDisplay`) — **not** the glyphs (separators, symbol, pattern layout), which come from the runtime's own ICU by locale. So for data-directed formatting on JS you either reassemble via **`formatToParts`** or apply the baked CLDR pattern yourself. In practice: a **thin shared pattern-applier fed by baked data** for the data-directed formatters, delegating only stable primitives. **That applier + the baked data is the conformance surface** the fixtures police (l10n's "the whole claim rests on divide-with-rounding").

**Exactness end-to-end — never touch a float.** The minor→decimal conversion is **`f8n`'s**, not `l10n`'s — it is scaled-integer arithmetic, not presentation (`../f8n/DESIGN.md` → *The representation model*). `l10n` formats the string it is handed and never derives the digits itself. `toDisplayAmount(money): string` returns an **exact decimal string** (built in bigint/string), *never* a JS `number` — `Number(bigint)` is lossy above 2^53 (~£9bn at any real scale) and re-introduces the float error the fixed-point `Money` exists to prevent. Modern `Intl.NumberFormat.format(string)` (NumberFormat v3, Node 18+/current browsers — verify runtime baseline) formats a decimal string exactly. Shared invariant both sides obey: **format from the exact decimal, never via a binary float.**

**Currency symbol — baked glyph, locale placement.** Symbol from `f8n`'s `Currency` (baked → no ICU symbol drift), but **position/spacing/sign are locale data** (prefix `£1.50` vs suffix `1,50 €`). So `formatToParts` + **swap the currency part** (ICU decides placement, you inject the baked symbol) — *not* prepend (prepend is only right for prefix locales). Edge: a currency ICU doesn't know → fall back to a baked CLDR currency pattern.

**Plurals — half-way house.** Evaluate baked **CLDR plural rules** (categories `zero/one/two/few/many/other`); handle **up to Welsh** complexity, no more exotic. Own it (platform plural APIs vary/absent). Same for select/gender if in scope.

**The guarantee is the fixtures' coverage** (oracle caveat, as in `c5n`): parity to thin fixtures = a *shared, invisible* blind spot. So the real work is **fixture coverage** — locales × formatters × the edges that break: negatives, zero, very large/small, symbol placement, per-currency fraction digits, plural-category boundaries, RTL.

## Format / parse — the boundary & the API
**Value-formatting lives in `l10n`, not on the `f8n` type.** `f8n`'s `Money`/temporal types carry only **invariant serialization** (exact, culture-free — wire/logs/debug; the grammar is pinned in `../f8n/DESIGN.md` → *Wire format*, and it is **strict in both directions** — the leniency below is the *human* boundary and must not share a parser with it). All **locale-aware format *and* parse** is `l10n`, *imported where used*:
- **TS:** free functions — `formatCurrencyShort(money, locale)`, `parseCurrency(str, locale)`. A `<MoneyInput>` (`../lattice/`) imports them and applies to the bound `Money` (idiomatic; binding unaffected). *(Named `MoneyInput`, not `CurrencyInput` — the bound type is `Money`; `Currency` is a separate primitive, and that name reads as a currency picker.)*
- **C#:** extension methods → `money.Format(locale)` reads like a method (a `using` brings them in scope).
- **Why not methods on `Money`:** tree-shaking (north star). Formatting-as-imported-functions bundles only the formatters you use; methods on `Money` would drag the whole formatting engine + CLDR data into every bundle that touches `Money`. (Also: a `Money.format` that quietly means *one* locale's short format is a convenience, not a model.)

**The locale never supplies the currency.** Every signature above takes *both* a `Money` and a `locale`, and that is load-bearing rather than incidental: the currency comes from the **amount**, and the locale decides only how it is shown. Inferring one from the other — rendering a USD amount with `£` because the viewer is `en-GB` — is the silent internationalisation failure, the kind that formats cleanly and reads plausibly and is wrong. The API shape is what makes it unavailable. The two axes are orthogonal, and the only territory→currency link is `Country.defaultCurrency`, which is a form pre-fill and not a rule about an amount that already exists. Note also that presentation varies by locale *and* currency **together** — USD is `$` in `en-US` and `US$` in `en-GB` — so neither one alone determines the rendering. See `../f8n/DESIGN.md` → *Currency and locale are orthogonal*.

**Cash rounding is not a formatting concern.** CHF rounds to 0.05 in cash but carries two decimal places for accounting. That is a fact about the *value* and belongs to `f8n` (an explicit `Money.RoundToCash`, not a display rule) — a formatter that quietly rounded to a cash scale would be changing the number it was asked to render. `l10n` shows what it is given.

**`currency-short` = compact** (`£1.2k`), **not** narrow-symbol. A **display + human-input** pair, **lossy** (`£1,234 → "£1.2k"`, so parse∘format ≠ identity) — **never a wire/persistence format**. Compact is deep: the *magnitude grouping* is locale-specific (en `k/M/B`; Indian **lakh 10⁵ / crore 10⁷**; CJK **万 10⁴ / 億 10⁸**) and CLDR compact forms are **plural-sensitive** → pulls in baked compact data + the plural machinery.

**Format is strict, parse is lenient — separate specs, not inverses.** Output = one canonical form per input (fixtured, exact). Input = a deliberately permissive human-input grammar per locale (case, whitespace, locale decimal separator `1,2k` vs `1.2k`, accepted suffixes). **Real parsing is narrow — only compact money + decimal (`1.2k`).** Everything else is lightweight **input hygiene** (char restriction, trim), not parsing; **date/time is format-only** (pickers hand back an `IsoDate` — no ambiguous free-text date parsing); `plural`/`select`/`enum` don't parse.

**Parse lowers text to digits; `f8n` converts them.** The split follows the same rule as formatting — `l10n` owns the **locale grammar** (separators, symbol, grouping, suffixes, whitespace, case) and lowers what the user typed to a plain decimal string; `f8n` converts that to minor units and decides whether it fits the currency's scale. So `l10n` never divides by `10^dp`, and never decides what is representable. When the value does not fit — `12.345` in GBP — `f8n` returns a **validation failure**, and `l10n`'s job is to render it in the user's locale ("GBP has 2 decimal places"), not to invent the rule or quietly round. Short input pads and redundant zeros are free (`12.3` and `12.3400` are both accepted), because the test is on the value, not the keystrokes — see `../f8n/DESIGN.md` → *The representation model*.

**Display formatting and edit formatting are different functions (2026-08-22).** A displayed value is fully decorated (`£1,234.57`); a value being *typed into* usually suppresses or carefully manages grouping so the caret does not jump under the user. Both are l10n's, and a money input consumes both — expose them as such rather than making the component reconstruct one from the other.

**A plain-decimal money parse is in scope (2026-08-22) — a bounded addition.** The "real parsing is narrow" line above holds for *compact* forms, but a money input needs ordinary locale-aware decimal parsing: `1,234.57` (en-GB) versus `1.234,57` (de-DE) — strip grouping, map the locale decimal separator, validate the fraction digits against the **currency's** decimal places, produce exact minor units. That is materially more than "input hygiene" and materially less than a general number grammar. The surrounding boundaries are unchanged: **no free-text date parsing** (pickers hand back an `IsoDate`), no general number grammar, `plural`/`select`/`enum` still don't parse. Consumer + editing-state model: `../lattice/DESIGN.md` → *Flagship: `MoneyInput`*.

## Interpolation & hints
One universal construct: **`{arg:hint}`** — `arg` names the parameter, `hint` selects the formatter. `"{limit:currency} per institution"`.

**The hint *is* the type.** Each hint maps to an `f8n` type, so `c5n` emits a typed parameter — `{limit:currency}` → `limit: Money`. Pass the wrong type or omit it → **compile error**. That's where the "typed" north star comes from.

**Value hints** — `hint = name ('-' param)?`, where `param` is an integer (digit count) *or* a variant keyword:
| hint | type | param |
|---|---|---|
| `currency`, `currency-short`, `currency-N` | `Money` | `short` = compact/narrow (TBD which); `N` = display dp (e.g. `currency-0` whole-pound) |
| `number`, `number-N` | `FixedDecimal`/number | `N` = fraction digits |
| `percent-N` | `Percentage` | `N` = fraction digits |
| `date-{variant}` | `f8n.IsoDate`/`DateOnly` | CLDR lengths `short`/`medium`/`long`/`full` |
| `time-{variant}` | `f8n.IsoTime`/`TimeOnly` (timestamp → `IsoDateTime`) | CLDR lengths |

**Selector hints** — `plural` and `select`, carrying `|category=text`; their variant text **nests further `{arg:hint}`**:
```
{count:plural|one={count:number-0} item|other={count:number-0} items}
{gender:select|male=…|female=…|other=…}
```
- Plural drives on a **named arg** (`count:plural`, *not* an arg-less `{plural|…}`), so it knows which number selects.
- Categories are the **target locale's** set (en author writes `one`/`other`; cy expands to all six) — the translation pipeline generates the target's categories; runtime falls back to `other`.
- **Plural couples to display precision:** the format hint's digit count *is* the plural's `v` operand — `number-0`→v0→"1"→`one`; `number-2`→v2→"1.00"→`other`. Rule: when one value is both pluralised and displayed, **a single digit-count governs both** (else "1.00 item").

**Escaping — the grammar does 95%, a 3-char escape set does the rest.**
- **Prose is literal by context:** `|` `=` `:` are only structural *inside* `{…}`; in message text they're plain characters.
- **First-occurrence splits:** first `:` splits `arg`/`hint`, first `=` splits `category`/`value` — everything after is literal (so `one=you owe = £5` just works).
- **Minimal escapes:** `\{` `\}` (literal braces, since `{` always opens an interpolation) and `\|` (literal pipe *inside a selector value*; a pipe inside nested `{…}` is already unambiguous). Plus `\\`. **Backslash, not ICU `'…'` quoting** — apostrophes are everywhere (`l'eau`) and ICU's quote rules are notoriously confusing.
- Riders: **fixtures must cover escapes** (literal `{`/`|`/`\` per locale — the archetypal demo-passes-prod-breaks bug); the **translation pipeline protects structural tokens** — extract placeholders → translate prose only → reinsert (never let the LLM "translate" `{count:number}` or the escapes).

**Digits are static** (authoring-time, e.g. `percent-2`) — not a runtime arg; genuine variable precision is served by the value's own `FixedDecimal` scale ("format to the value's scale"), keeping the hint a fixed type/format. **Exact-value matches supported** — `=0`/`=1` checked *before* the category rules (`=0=No items` — distinct from the `zero` *category*, which is grammatical/Welsh-Arabic); parse wrinkle: a key starting with `=` splits on the *second* `=`. *(Also resolved: `date-*` → `f8n.IsoDate`/`IsoTime`/`IsoDateTime`; `currency-short` = **compact** — see Format/parse.)*

## Codegen structure (candidate — 2026-07-04)
How `c5n` emits l10n, from the c5n l10n stress-test. **Candidate** — a codegen-native redesign, deliberately *not* the conventional translation-client / string-resolver shape, which retrofits codegen onto a hand-first design; this is designed *for* codegen from day one. **Not yet validated against a real message set — pressure-test before settling: `codegen-shape-test.md`.**

Three parts:
- **Generated — a `tree<T>` of typed shims.** The namespace tree (dir/file = namespace) emits as nested scopes (C# nested static classes, TS nested modules); each message leaf is a **thin typed façade** whose signature comes from the hints (`{limit:currency}` → `limit: Money`), delegating to the runtime. The typed signature is the one irreducibly-generated thing — the "typed" north star.
- **Generated — the message as *data*.** The parsed `{arg:hint}` message (params + a recursive list of parts: `literal | format-call | selector`) emitted as a plain data value. `c5n` never parses the DSL; an **l10n front-end lowers it to this structured model** upstream.
- **Hand-written — one `render` interpreter per language.** Walks the parts, calls the formatters, evaluates plural category, recurses into selector branches — plus the formatters + pattern-applier + `PluralCategory`. **This is the entire conformance surface** (exactly "conformance by verification"): language-neutral message data + two hand-written interpreters, fixture-tested.

**Why (perf + conformance):** the DSL is parsed to data **at build time**, so runtime never re-parses (a runtime resolver would, per call); a **single** interpreter per language keeps the conformance surface tiny — vs inlining thousands of message bodies, the cross-language-identical burden the north star can least afford. Near-inlined speed, minimal surface, simple codegen. See `../c5n/DESIGN.md` → **Stress-tested against l10n**.

**Open (C#):** nested static classes give typed access, but shipping only *used* locales is the separate satellite-assembly / trimming question (Tree-shaking agenda item).

**Correction from the pressure test (2026-08-27): the three parts above describe *one* tree where there are two.** The **typed-shim tree is locale-neutral** — one of it, signatures derived from the canonical (en-GB) hints — while the **message-data trees are per locale**, since Welsh carries six plural branches where English carries two. Different leaf types, different output layouts, different tree-shaking needs, emitted by `c5n` from related but distinct sources. It also implies a rule this doc left unstated: **a signature derives from the canonical message only, and every locale's data must conform to it** — checkable at build time, and what makes the pipeline's *protect structural tokens, translate prose only* load-bearing rather than merely tidy, since a translator who introduced an interpolation would otherwise produce data the shim cannot call. Full case list and what is still unwalked: `codegen-shape-test.md`.

## Translation pipeline
**Machine-generates → human-gates → CD-gate**, checked-in and PR-reviewed (same shape as `c5n`'s generated code — deterministic diffs are the review surface).

**Canonical storage (en-GB) = the dev interaction point.**
- An **en-GB directory**; **sub-dirs + files provide the namespacing** (the dir/file tree *is* the namespace tree).
- Files are `key = value` **JSON**. Devs edit here.
- **Every regen sorts files by key** → deterministic ordering → clean git diffs.

**Per-locale storage** mirrors the en-GB dir/file structure. Each entry:
```json
"key": { "value": "…", "sourceChecksum": "…", "translated": "<DateTimeOffset>", "approved": false }
```

**Translation run** — iterate en-GB; per key compare current source checksum vs stored `sourceChecksum`:
- **missing or checksum differs** → call the **Anthropic API**, fill the translation, set `translated`, update `sourceChecksum`, **`approved: false`** *(the linchpin — a source change un-approves, or stale text ships past the gate)*.
- **checksum matches** → no-op.
- Placeholders: **repair `{arg:hint}` after the round trip, then validate** — the set (by identity) must match source; a *dropped* placeholder isn't repairable, so on mismatch reject/retry, never write. (Repair keeps LLM context/quality; validate backstops drops.)
- **Plurals expand to the *target's* categories** — Welsh's six from English's two; each variant translated + placeholder-checked.

**Human review** — adjust `value`, set `approved: true`. `sourceChecksum` stays pinned to what was approved, so the next source change re-gates it.

**Deploy gate** — blocks release if *any* string is unapproved.

**Housekeeping & choices:**
- **Orphan pruning** — a key removed from en-GB → prune the per-locale entries (the regen already rewrites every file). **Rename = delete + add → re-translate from scratch** (prior human work on the old key is lost; rename sparingly).
- **Clobber policy** — a re-translate **never clobbers**: keep the human `value`, set `approved:false`, and store the fresh machine translation in a **`suggestion`** field. The reviewer then chooses — accept their old (minor source change), take the `suggestion` (material change), or edit. Never silently overwrite, never blindly keep.
- **Context for the translator** — three tiers, cheapest first: (a) **the key path is context** (`account.open.button` → feed the full key to the LLM prompt, free); (b) an **optional `{ value, context }`** form for strings that genuinely need a note (plain `key = "value"` stays the common shorthand); (c) **a screenshot** — the best context — see the translator UI below.

## Translator UI (l10n × a11y — seam now, room later)
The pipeline's **human-gate surface**: land on a field, a shortcut opens a panel showing **key + value + per-locale status + a screenshot** of where the string renders. Edit → the app splits value/hints, stores → **creates a PR** (which flows through `approved:true` + the deploy gate). Two strong ideas:
- **Screenshot-as-context comes from the `a11y` audit.** The audit already walks the live app per-control; if controls **carry their l10n key**, it captures a screenshot per key — reusing a11y infra for l10n. (Cross-project: `a11y`'s design must include the **l10n-key ↔ control mapping**.)
- **Placeholders as atomic chips** — the human edits *around* protected `{arg:hint}` chips they can't delete or retype → placeholder integrity on the human path by construction (vs the LLM path's repair+validate).

**Seam vs room:** build the *data linkage* now — `l10n key ↔ control ↔ screenshot ↔ per-locale status`, and the a11y audit emitting the key — the full UI is a later room. Caveats: **screenshots regenerate on each audit/CI run** (else they rot); **non-visual strings** (error toasts, aria-only, un-captured states) have no screenshot → fall back to key-path + optional context.

**Compliance / trust** (`design-rigour`; customer-facing content + human gate is the right control):
- **Source strings → a third party (Anthropic)** — fine for public UI copy (display-destined), so the rule follows: **no secrets / PII / internal notes in translatable strings.**
- **Stricter-than-LLM content** — financial promotions, legal disclosures, regulatory error text: a mistranslation is a *compliance* event, not a typo. A per-string `requiresProfessional` marker (or namespace convention) routes those to a human translator, still through the same approval gate.

## Runtime & integration
Surface beyond formatting/messages (much of it C#-side glue; each item has been needed in practice):
- **Locale scope — never `CurrentCulture`.** An `IDisposable` scope sets the locale per request/loop/operation; **`AsyncLocal`-flowed** (thread-static would leak one request's culture into another across `await` — a real correctness bug). "Controlled ambient": the scope is the ergonomic default (`format(money)` reads it) with an explicit override (`format(money, locale)`). Same discipline as f8n's *injected clock, never `DateTime.Now`*. (TS has no `CurrentCulture` temptation — `Intl` takes locale per call, Vue holds a reactive ref — so this is mostly a C# discipline.)
- **m2m propagation** — locale flows across service boundaries via a header (like trace context); extensions to set/read it, so the scope survives service → service.
- **JWT locale extraction** — pull the locale claim from a JWT (both langs) → feed the scope.
- **Setup extensions** — C# DI (`services.AddL10n(…)`), Vue plugin (`app.use(…)`, plain-TS options, framework-uncoupled).
- **Analysers** — Roslyn (C#) / ESLint (TS) flag problems (hard-coded strings, missing keys, bad hints) at build.
- **Enum localization** — each enum member gets a localized label via the key convention `EnumName:Member`; typed access generated. (The "helpers (C# enums)" from the original sketch.)

## Assumptions this library can't make
A formatter with a fixed locale, a single currency and bounded amounts can be entirely correct under its own rules and still be unusable as a library. Dropping each of those assumptions is where the whole difficulty lives.
- **Multi-locale from the start** — so suffix-currency locales (de/fr) and Welsh plurals are in scope, not bolt-ons.
- **dp is currency-specific, nothing more** — the money model is `f8n`'s currency-dp-exact `Money` (a fixed 6-dp-internal convention doesn't generalise; see `../f8n/DESIGN.md`). Sub-currency precision is explicit `FixedDecimal`.
- **Any magnitude** — the library can't assume bounded amounts, so exactness must hold to arbitrary size (the `Number()`/2^53 leak stays hidden while amounts are bounded and bites the moment they aren't → exact-string throughout).
- **Any locale** — so symbol placement, grouping, plural rules are all *data*, never hardcoded (prepend-the-symbol was fine for prefix locales, wrong in general).
