# f8n — design

Standalone, broadly-reusable **domain primitives — Country, Currency, Money** — generated cross-language (C# + TS) from canonical data. The base layer the rest of the stack sits on (`l10n`, `doppel`, `yield` all consume it). Personal open-source (destined).

> **Name:** **`f8n`** — numeronym for *foundation* (f + 8 + n), matching the house style (`l10n`, `a11y`). Also sidesteps the Zurb Foundation (CSS framework) collision. Quicker to type; reads as a family with the rest of the stack.

> ⚠️ **UNRESOLVED — licence conflict in the data sourcing (blocks the data pipeline; decide before the walking skeleton bakes it).** Debian **`iso-codes` is LGPL-2.1** (pycountry is LGPL *because* it embeds it). Embedding iso-codes-derived tables as **generated code inside an MIT `f8n` is murky** — and the EU **sui-generis database right** weakens the "facts aren't copyrightable" defence. `doppel/DESIGN.md` did this analysis (CC0-over-CC-BY-SA); this doc never did.
> **Likely resolution: go CLDR-only** (Unicode licence, permissive) — CLDR already carries territory/currency codes, official names, and everything relational the split below routes through it, so `iso-codes` is only doing "code lists + official names" that CLDR also has. Drop `iso-codes`, or demote it to a **non-redistributed** build-time cross-check.
> *Time-sensitive: this is training-data knowledge about licences — **verify current licence texts** before wiring the pipeline.* See the **Data sources split** decision + the **Source pipeline** agenda item.

## North star (every decision serves these)
1. **Cross-language conformance** — C# and TS produce **identical** output: *provable by construction* for the integer core (add/sub/mul-by-int on scaled integers), and **golden-vector-verified** for the one divergent surface (`divide-with-rounding`). Same DNA as `l10n` (verified against comprehensive vectors — the guarantee is the coverage, not all-inputs).
2. **Canonical data, kept current** — sourced from authoritative places (CLDR, Debian `iso-codes`); a cron rebuild raises a PR on any upstream diff (data current, changes reviewed — the machine-generates → human-gate signature).
3. **Codegen'd data, hand-maintained behaviour** — `c5n` generates the canonical **data** (currency/country reference tables from CLDR/iso-codes) into a **typed structure**; the **behaviour** (money math, parsing, resolution) lives in **hand-maintained classes** that consume that structure, written once per language and verified identical by golden vectors. Typed throughout → wrong usage is a compile error. *(The c5n split, applied here: generate the data + typed surface; hand-write the algorithm — see `../c5n/DESIGN.md` → Generation model. Behaviour is NOT codegen'd.)*
4. **Useful beyond localisation** — a general-purpose primitives library, not an `l10n` internal.

## Scope boundary — what `f8n` stores vs what it only types
The sharpest recurring line in the design:

> **`f8n` stores canonical *identity / reference* data** (ISO country & currency, CLDR formatting facts) — single-sourced, stable, fit for the cron→PR pipeline.
> **It does *not* store market- or policy-driven *values*** (FX rates, tax schedules) — for those it owns the **type + behaviour**, and the values are **supplied from outside**.

FX (fast, market) and tax (policy, jurisdiction-specific, no canonical commodity-level source) both fall on the "type here, values external" side. Owning those datasets would blow scope, lack a canonical source, go stale, and — for tax — create a **compliance liability** (wrong rate → mis-charged VAT). See the `TaxRate` and `ExchangeRate` decisions.

## The primitives
Core set: **`FixedDecimal` · `Rational` · `Money` · `Country` · `Currency` · `Locale` · `PhoneNumber` · `IsoDate`/`IsoTime`/`IsoDateTime`** + the rate types below. **Domain taxonomies** (industry codes like SIC, credit-rating scales like Fitch, …) are **out of scope** — they belong in the consuming/domain layer and are *generated by* f8n's codegen + `EffectiveDated` tooling, **not shipped as f8n types** (that's how a shared library's type surface multiplies). See `data-lookups.md`.

**Numeric**
- **FixedDecimal** — a general **fixed-point decimal carrying its own scale**; exact, no bignum lib. The substrate `Money` and the market-rate types build on, **and the explicit precision / calc space**: FX intermediates, accrual ledgers, unit prices (e.g. fuel £1.459/L) — anywhere precision above a currency's dp is wanted, at a scale the *consumer* chooses. Home of the shared C#/TS fixed-point arithmetic + **divide-with-rounding** conformance surface. (The "some kind of Decimal" wanted for `Rate` at the very start; answers "does `Decimal` carry a per-instance scale?" → yes.)
- **Rational** — an **exact fraction, `(num, den)` as big integers** (`bigint` / `BigInteger` — *already in* for intermediates, so no new dependency; "no bignum lib" above is about *decimal* bignums, not big integers). The substrate for **proportions that must stay exact under reuse** — `Percentage`/`TaxRate`, and `yield`'s compounding. It is the *only* representation that preserves **fraction identity**: `1/3 · 3 == 1` exactly, `0.999… == 1` (it never materialises the recurrence into a decimal that then falls a ulp short), and **recurrence is decidable** — strip 2s/5s from `den`; remainder `1` ⇒ terminating, else recurring (a *denominator* fact, not an unsound digit-scan). Where `FixedDecimal` fixes a scale and rounds each step, `Rational` defers all rounding to the single apply boundary. **Canonical form:** gcd-reduced, `den > 0`, sign on `num`, zero `= 0/1`, integers keep `/1` ⇒ equal values have identical encodings, so `==` is component-compare and wire/DB equality is string equality. **Serialised as one canonical string `"num/den"`** (see the decision — *not* two ints: big-integer num/den don't fit a JSON number or an `int64` column).
- **Money** — value + currency, an **exact integer count of the currency's minor units** (GBP 2 dp, JPY 0, BHD 3). Add/subtract are exact; precision-losing ops (× rate, ÷) take a `RoundingMode` → `Money` at currency dp. **Splitting is different: `allocate` *conserves*** — parts sum to the whole exactly, via a caller-chosen `AllocationRule`, not a `RoundingMode` (see the representation model). **No hidden working precision** — need sub-currency precision (FX processing, accrual)? Enter `FixedDecimal` explicitly, work, convert back to `Money` with a mode. Behaviour: arithmetic, comparison, rounding, and **invariant (culture-free) serialization only** — all *locale-aware* format/parse is `l10n`, imported (tree-shaking; see `../l10n/DESIGN.md`).

**Identity** (ISO code lists via `iso-codes`; relational/structural attributes via CLDR — see Data sources)
- **Country** — ISO 3166: **alpha-3 (id / table key)** / alpha-2 / numeric; official name; **calling code** (E.164); **default currency** + **capital's civil timezone** (a single well-defined representative zone, CLDR). *Defer:* subdivisions (3166-2) **+ per-subdivision timezones**, flags, containment.
- **Currency** — ISO 4217: alpha-3 (id) / numeric; name; **default symbol** (canonical only — locale-specific presentation stays `l10n`'s); **minor-units / exponent** + **cash-rounding** (CLDR supplemental — CHF 0.05). *Defer:* historical/withdrawn.
- **Locale** — BCP 47 tag: parse / validate / **canonicalise** (likelySubtags) / match; decompose to language·script·region. **Identity only** — formatting / plurals / display-names are `l10n`. (Platform `CultureInfo`/`Intl` aren't consistent across OS/ICU versions, so baking locale identity is a conformance win, not duplication. Locale is easily mistaken for an `l10n` concern; it isn't — matching and canonicalisation have no presentation in them.)
- **PhoneNumber** — simple wire-transport pair `{ number: string, country: alpha-3 }`; E.164 = `+` + the country's calling code + number. Simple input parsing (not libphonenumber-scale). **Stores the country explicitly** because calling-code→country is 1:many (`+1` = US/CA/NANP, `+44` = UK + crown dependencies) — country→calling-code is the safe 1:1 direction.

**Temporal** — a **TS-side polyfill** bringing TS up to C#'s native value types (C# has these already; `c5n`'s type-map binds one logical type → native C# / provided TS):
- **IsoDate** ↔ `DateOnly` — **civil, zone-less date** (the tax/policy temporal kind; see `data-lookups.md`).
- **IsoTime** ↔ `TimeOnly` — wall-clock time of day.
- **IsoDateTime** ↔ `DateTimeOffset` — an **instant, always offset/`Z`-bearing**. **Never a naked local datetime** (`DateTimeKind.Unspecified` / a zone-guessing JS `Date`) — that ambiguous middle re-introduces the BST-boundary bug. Three types (civil date / wall time / instant), *pointedly not* a floating-local-datetime.

Common characteristics: immutable value types; **ISO-8601 on the wire, parsed by strict regex over a *defined subset*** (own it — platform parsers are lenient/culture-sensitive/engine-inconsistent; strict regex = conformant-by-construction, both langs accept/reject identically). Helpers added as needed (representation-first); any *math* helper (add-days, diff) is a conformance surface → fixture it. **Open:** pin the accepted ISO subset (offset forms `Z`/`±HH:MM`, fractional-seconds precision; reject week/ordinal dates).

Rate-like values: **distinct nominal domain types over a shared exact substrate** (the type says what the thing *is*; the arithmetic/conformance machinery is shared once). Proportions (`Percentage`, `TaxRate`) sit on **`Rational`** — exact fraction identity; the market rate (`ExchangeRate`) sits on **`FixedDecimal`** at a consumer-chosen scale (a treasury desk's 8 dp is a *chosen precision*, never a clean fraction). `%` / bp are constructors + formatters (display → `l10n`), never types.
- **Percentage** — plain **dimensionless proportion**, backed by a **`Rational`** (so `4.52%` is exactly `113/2500`, and `1/3` stays a third — no `0.0452`-style materialisation, no `1/3·3` drift). **Apply-only in `f8n`:** `Money × p → Money`, same currency (VAT, fee, discount). **No `Percentage × Percentage`** — compounding grows the denominator and lives in `yield` on `Rational` directly (see the apply-only decision).
- **InterestRate** — a `Percentage` **+ a time basis** (p.a.). *Cannot* be applied to Money until a period turns it into a factor — carries a real time dimension, hence its own type.
- **ExchangeRate** — a ratio **+ a `(from, to)` currency pair**; the *only* rate that changes currency, via `Money(A).convert(rate) → Money(B)`. Takes a **directly-provided rate (first-class)**; preloading a dated series is optional. `f8n` owns type + behaviour; *values* come from outside (market data).
- **TaxRate** — a `Percentage` **+ `(jurisdiction, tax-type, category)`** — e.g. `(GBR, VAT, standard) = 20%`. Scoped to **transaction taxes** (rate × amount: VAT/sales/GST/withholding), **not** an income/corp/CGT/payroll *engine*. `Money.taxOf(rate)` takes a rate directly (first-class); the dated schedule is optional. `f8n` owns type + apply-behaviour (net↔gross); *values* external; ships only a **static, non-authoritative dated sample**. Key on **`Country`** for now, designed to widen to a `Jurisdiction` hierarchy (US sales tax is sub-national + stacking) later.

**Rates are dated facts, not scalars.** The commonest money bug in the wild is a hardcoded `0.20` — correct the year it was written, silently wrong when the rate moves (UK VAT: 17.5% → 15% in 2008 → 17.5% in 2010 → 20% from 2011-01-04). So every rate value is `(…, validFrom, validTo?)`; `Money` is timeless, **rates are temporal**. Consequences:
  - **Generalises across rate types** — FX is point-in-time, interest rates change, tax bands get reclassified. Dating is a *shared* concern, not a `TaxRate` special case.
  - **The date lives in *resolution*, not the math** — schedule + date → resolved `Percentage`; then `Money × Percentage` is date-free. Temporal logic stays in one place (the lookup).
  - **Valid-time only, not bitemporal** — effective dates yes; "when we learned it" (knowledge time) is a complexity sink, skip unless `yield` forces it.

## Data & lookups → `data-lookups.md`
The data side — what `f8n` ships vs types, the `EffectiveDated<Key, Value>` lookup, consumer-data codegen, and the temporal model — lives in **`data-lookups.md`**. In brief:
- **Building blocks, not an engine** — `f8n` ships canonical identity (ISO country/currency); rate *values* are **supplied** via the `EffectiveDated` lookup (dependency inversion). Direct value first-class; lookup optional.
- **Consumer data → typed accessors** — a build tool turns consumer YAML into **named constants that are `f8n` types** (one-way dep, "ref sticks", value-based API holds no ref).
- **Timeless value vs named binding** — the series attaches to the *name*; all named rates generate as a **uniform `EffectiveDated` series** (constants normalised in authoring only).
- **As-of API** — `taxOf(series, date)` / `asOf(taxPoint)` basis; "current" = resolve-as-of-a-date (never newest-row); default "now" via injected clock.
- **Temporal model** — tax = civil `DateOnly` (no tz), FX = UTC instant; tz derived from the rate's jurisdiction, never a call param.

## The representation model — everything reduces to integers
`Money` (currency scale), `FixedDecimal` (chosen scale), and `ExchangeRate` (`FixedDecimal`-backed) are **scaled integers**; `Percentage`/`TaxRate` are **`Rational`** — a `(num, den)` integer pair. Either substrate is integers underneath, so add/subtract/multiply-by-integer are **identical by construction** across C# and TS.

**Minor ↔ major digits is `f8n`'s, not `l10n`'s.** Turning `1234` minor units into the exact decimal text `12.34`, and back, is *arithmetic on scaled integers* — multiply or divide by `10^dp`, exactly — not presentation. It lives here, once, where the golden vectors already are. `l10n` consumes the exact decimal string and applies locale glyphs, grouping and placement to it; it never derives the digits itself. Two implementations of this conversion would be two conformance surfaces obliged to agree, in precisely the place a binary float silently ruins the answer. See `../l10n/DESIGN.md` → *Format / parse*.

**Parsing user text: the currency's scale is a validation rule, not a rounding site.** Someone typing an amount is not performing a calculation, so the no-silent-rounding discipline — which exists because precision leaks across *chained arithmetic* — does not mean "reject anything that is not exactly `dp` digits". The rule is about the **value**, never the keystrokes:

- **Fewer digits than the scale is fine.** `12.3` in GBP is `1230` minor units — exact. Pad and accept; rejecting it would be hostile and buys nothing.
- **More digits are fine when the value still fits.** `12.3400` is `1234` minor units exactly. The extra characters carry no value, so they cost nothing.
- **A value that cannot be represented at the scale fails validation.** `12.345` in GBP is `1234.5` minor units — not an integer — so it is rejected with a message naming the scale ("GBP has 2 decimal places"), never silently rounded to `12.34` or `12.35`.

That is the **human** boundary, and it is the lenient one. The **wire** boundary is strict in both directions — see *Wire format* below; a producer is not a person typing, and the two must not share a parser. One test rather than a digit count: **convert to minor units exactly, and accept iff the result is an integer.** No heuristics, no character counting, and the same answer in both languages. The failure is a *validation result* a UI renders — localised by `l10n`, and carrying a stable rule identity so a client-side check and a server-side one are recognisably one rule (`../c5n/DESIGN.md` → *Generated rules carry stable identity*).

**`Money` is exact at its currency's dp — no hidden working precision.** A `Money` is an integer count of minor units at the currency scale (GBP 2, JPY 0, BHD 3). Add/subtract never lose anything. **Precision is opt-in, not global:** where a calculation needs more (FX processing, accrual, triangulation-style multi-hop), you *explicitly* enter `FixedDecimal` at a scale you choose, do the work, and convert back to `Money` with a rounding mode. This replaces the earlier "6 dp everywhere, settle at the boundary" model — that was an over-generalised FX/euro-conversion habit (rates were 6 sig-fig, triangulation mandated ≥3 dp intermediates); the precision belongs to the *FX/calc context*, not to every `Money`.

The precision-losing operations — **× rate, ÷** — take a `RoundingMode` and land back on the target currency's dp (**`allocate/split` is separate — it conserves, see below**):
```
result_minor = round( money_minor × rate_scaled / 10^(rate_scale) , mode )   // → currency dp
```
Integer multiply, then integer divide-with-rounding. **The whole cross-language conformance claim collapses onto one shared function: divide-with-rounding.** That function is what the golden-vector harness targets; everything else can't diverge.

**A `Rational` applies the same way — `den` in place of `10^scale`.** `Money × Percentage` is `money_minor × num`, then divide-with-rounding by `den`. It is the *identical* shared function; the denominator simply isn't restricted to a power of ten. So making `Percentage` exact **adds no new conformance surface** — it still collapses onto `divide-with-rounding`, and `Rational`'s own arithmetic (gcd-normalise, over the big integers already present) is deterministic in both languages. The one place exactness could still be lost — compounding a stored fraction, where denominators grow — is deliberately kept out of `f8n` (apply-only) and pushed to `yield`.

**Allocation is a *conserving partition*, not a rounding op.** Splitting a `Money` into parts — equal N-way, or weighted by `Rational`/`Percentage`/int — must **sum back to the whole exactly**: `sum(allocate(m, …)) == m`, no minor unit created or destroyed. Rounding each part independently *doesn't* conserve (`£100/3 → £33.33 × 3 = £99.99`, penny lost); `allocate` instead **floors each exact share to minor units, then hands out the leftover units** per a caller-supplied **`AllocationRule`**. The rule is **parameterised — f8n can't know the mandated method in advance** (same house pattern as caller-supplied `RoundingMode` / FX scale); and unlike `RoundingMode` it has **no default** — a silent apportionment method risks the same mandated-method non-compliance the currency-dp decision already guards against, so the caller must choose. Built-ins: **`LargestRemainder`** (Hamilton — leftover units to the largest fractional remainders, ties by ascending index), **`Designated(i)`** (one nominated part / ledger line absorbs all residual), **`Sequential`** (first parts absorb). Weighted shares are exact `Rational`s (`m × wᵢ / Σw`) floored to minor units, so the *only* rounding is the deterministic remainder hand-out. **Sign-symmetric:** `allocate(−m) == −allocate(m)` componentwise. A total order with an explicit tie-break ⇒ `allocate` is another **golden-vectored conformance surface**, identical across C#/TS by construction.

**Intermediate precision:** `money_minor × rate_scaled` overflows `int64` for large amounts, so intermediates use **arbitrary-precision integers — TS `bigint`, C# `BigInteger`** — *not* native `decimal` (whose rounding we'd otherwise have to prove matches). Both languages then run the identical integer algorithm. (`Int128` is a later perf option, not needed for v1.)

**FX precision is a consumer choice.** `ExchangeRate` is a `FixedDecimal` at a scale the consumer picks — a treasury desk wants 8 dp, a retail app 5, an accrual ledger something else. `f8n` provides the functions and lets the caller decide the right precision + rounding for their rule; it never bakes a magic scale.

**Rounding:** a `RoundingMode` enum — default **`HalfEven`** (banker's), **`HalfUp`** ("normal") also available — passed to every precision-losing op (Money × Rate, any divide). (`allocate/split` doesn't take a `RoundingMode` — it conserves via an `AllocationRule`; see above.)

## Wire format — strict in both directions

These types cross process boundaries — HTTP bodies, logs, queues, DB columns — and the form they take there is a **published contract**, so it is pinned rather than left to each serialiser.

**Readable, because a wire body is something a human debugs.** `{"amount":"12.34","currency":"GBP"}` — not a minor-unit integer that means nothing without knowing the currency's scale. It costs a little (below) and buys a payload diagnosable in a network tab and a live API page a third party can read. *Rejected: `{"minor":"1234", …}`* — canonical by construction, and unreadable in exactly the moment anyone needs it.

**Exact, because a number is not a display string.** Every numeric payload is a **string, never a JSON number**. A JSON number is a float64, and `Rational`'s big-integer denominators, `FixedDecimal` at a treasury scale, and large `Money` values all exceed what it holds. One rule for every type, so nothing rests on judging whether *this* value could get big.

### The amount grammar — full precision, one representation

**Always exactly the currency's decimal places, zeros included:** `"12.30"`, `"0.00"`, `"1234"` (JPY, 0 dp), `"12.340"` (BHD, 3 dp). Simple to state, simple to check, and it helps the reader — `"0.00"` says *money at 2 dp*, where `"0"` says nothing. Anything short is **wrong**, not merely terse.

**The parser is fussy: anything else is an error, never a coercion.** Deliberately not lenient — this is the decision already taken for the temporal types (strict regex over a defined subset, *conformant-by-construction, both langs accept/reject identically*), for the same reason. A lenient parser lets two producers emit different bytes for one value, both "work", and the contract quietly becomes a dialect. Strictness is also what preserves **wire equality = value equality**, the property `Rational`'s canonical string was chosen for.

For a currency with `dp` decimal places:

```
dp = 0:   -?(0|[1-9][0-9]*)
dp > 0:   -?(0|[1-9][0-9]*)\.[0-9]{dp}     # exactly dp digits — never fewer, never more
```

| rejected | why |
|---|---|
| `"12.3"` (GBP) | short; precision must be full |
| `"12.345"` (GBP) | not representable at the scale |
| `"+12.34"` | one representation only — no leading `+` |
| `"012.34"` | leading zeros |
| `".34"` | integer part required (`"0.34"`) |
| `"-0.00"` | a signed zero is not a second zero |
| `"1,234.56"` | grouping is presentation, and presentation is `l10n`'s |
| `12.34` (JSON number) | float64 |

**Sign is part of the format, not an afterthought.** A leading `-`, and nothing else — no `+`, no parentheses, no trailing sign; those are display conventions and belong to `l10n`. **Zero is unsigned:** `Money` is an integer count, `-0` is not a distinct value, so `"-0.00"` is rejected on input and never emitted. Without that rule one value has two encodings, and wire equality stops meaning value equality.

**The amount cannot be validated without the currency**, since `dp` comes from it, and JSON field order is not guaranteed — so `fromJson` reads both fields before converting, and both languages do it in that order to accept and reject identically.

### Reference types travel as their key
A `Country`, `Currency`, or any other keyed table row is sent as its identity — `"GBP"`, `"GBR"` — never as an inlined record. `PhoneNumber` already does this (`{ number, country: alpha-3 }`), and it is what c5n emits in generated code, so one rule serves both.

### Enums travel as their member name
An enum is serialised as **text** — `"VAT"`, `"Standard"` — never as an ordinal. A number on
the wire would mean the member list's *order* were part of the contract, so inserting a
member would silently move every value after it; the name is stable under any reordering,
and it is readable in the place a wire body actually gets read. C# must therefore be
configured to write enums as strings rather than take the serialiser's numeric default; TS
gets it for free, since a generated enum's runtime value **is** its name (see
`../c5n/DESIGN.md` → *Enums*).

The consequence lands upstream, in `c5n`: **a member name is a published token**, so no
casing is applied to it anywhere between the schema and the wire, and enum members are
*declared* rather than collected from data — a typo that minted a member would mint a wire
token with it.

### Scale travels only when the type cannot supply it
`Money` never carries its scale — the currency has it. That is the general rule rather than a special case: **a payload carries only what its type cannot already tell you.**

- **Concrete types with a built-in precision** — the scale belongs to the type's identity, so the wire form is just the value string, under the same grammar with `dp` fixed by the type instead of by a currency. Preferred wherever a precision is common enough to be worth naming: the payload is smaller and more readable, and — the real gain — changing that precision becomes a **visible change to the type**, which is a contract change something can be versioned against, rather than a silent variation between two payloads that both parse.
- **The general `FixedDecimal`** — the scale is consumer-chosen and nothing in the type supplies it, so it **travels**: `{"value":"12.34000000","scale":8}`. Full precision still means **exactly `scale` digits**, so `{"value":"12.34","scale":8}` is an error in the same way a short `Money` amount is.

This is the representation model applied to the wire — *distinct nominal types over a shared exact substrate, where the type says what the thing is*. A fixed precision is one more thing the type can say, and saying it beats shipping it on every message.

**Follow-up — `ExchangeRate`.** It is the existing `FixedDecimal` consumer and is documented as sitting at a *consumer-chosen* scale, so it either carries `scale` like the general form or becomes a concrete type at a pinned precision. Decide when it is built; the rule above doesn't force it either way.

- **2026-08-25 · Scale travels only when the type cannot supply it** → resolves the `FixedDecimal` question left open by the wire-format entry below. **A payload carries only what its type cannot already tell you** — the rule `Money` already follows by taking `dp` from its currency, stated generally. So: **concrete types with a built-in precision** send just the value string (same grammar, `dp` fixed by the type), and the **general `FixedDecimal`** sends `{"value":"12.34000000","scale":8}` because nothing in the type supplies the scale — with full precision still meaning *exactly* `scale` digits, so a short value is an error there too. Concrete types are preferred wherever a precision is common enough to name: besides being smaller and more readable, a precision change then becomes a **visible change to the type** — something a contract can be versioned against — instead of a silent difference between two payloads that both parse. This is the representation model applied to the wire (*distinct nominal types over a shared exact substrate; the type says what the thing is*), with a fixed precision as one more thing the type says. **Follow-up:** `ExchangeRate` sits on a consumer-chosen scale today, so it either carries `scale` or becomes a concrete type at a pinned precision — decide when it is built.
- **2026-08-25 · Wire format: readable envelope, strict grammar, strings not numbers** → `Money` crosses the wire as `{"amount":"12.34","currency":"GBP"}`. **Readable wins** over the canonical-by-construction minor-unit integer, because a wire body is what a human debugs in a network tab and what a third party reads on a live API page. The costs are paid by rules rather than absorbed: the amount is **always exactly the currency's dp, zeros included** (`"0.00"`, `"12.30"`), which restores canonicality and so keeps *wire equality = value equality*; and the **parser is strict — anything else errors**, never coerces, matching the temporal decision (strict regex over a defined subset, both langs accept/reject identically) and for the same reason, that a lenient parser turns a contract into a dialect. **Sign is part of the grammar:** leading `-` only, no `+`, no parentheses, and **zero is unsigned** — `"-0.00"` is rejected and never emitted, or one value gets two encodings. **Every numeric payload is a string, never a JSON number** (float64 cannot hold big-integer denominators, treasury-scale `FixedDecimal`, or large amounts) — one rule, so nothing depends on judging which values get big. **Reference types travel as their key** (`"GBP"`, `"GBR"`), as `PhoneNumber` already does and as c5n emits. *Note the asymmetry with human input: the `l10n` boundary is lenient by design, the wire boundary is strict in both directions, and they must not share a parser.* *(The `FixedDecimal` scale question raised here is resolved in the entry above.)*
- **2026-08-25 · `l10n` does no money math; input scale is validation, not rounding** → the **minor↔major digit conversion is `f8n`'s** — scaled-integer arithmetic, golden-vectored here — and `l10n` formats the exact decimal string it is handed, never deriving digits itself. Two implementations of that conversion would be two conformance surfaces obliged to agree, exactly where a binary float silently ruins the answer. **Parse mirrors it:** `l10n` lowers locale text (separators, symbol, grouping, suffixes) to a plain decimal string; `f8n` converts it and enforces the currency's scale. The scale test is on the **value, not the keystrokes** — convert to minor units exactly and accept iff the result is an integer: `12.3` GBP pads to `1230`, `12.3400` is `1234`, and `12.345` **fails validation** with a message naming the scale rather than rounding. *(The no-silent-rounding rule it defers to is about precision lost across chained arithmetic; a single typed input is not a calculation, and applying the rule there would only be hostile.)*
- **2026-07-17 · `allocate` is a conserving partition with a parameterised rule** → splitting `Money` into parts (equal or weighted) **conserves**: `sum(parts) == whole`, exactly. A *different discipline from rounding* — `HalfEven`/`HalfUp` round parts independently and lose the odd unit (`£100/3 = £33.33 × 3 = £99.99`); `allocate` floors exact shares then **distributes the remainder** per a caller-supplied **`AllocationRule`**. **The rule is parameterised — f8n can't know the caller's mandated method in advance** (same house pattern as caller-supplied `RoundingMode` / FX scale), and **has no default** (a silent apportionment method risks mandated-method non-compliance — the caller must choose). Built-ins: `LargestRemainder` (Hamilton, index tie-break), `Designated(i)` (nominated ledger line absorbs residual), `Sequential`. Weighted shares use exact `Rational` math (`whole × wᵢ / Σw`) floored; **sign-symmetric** (`allocate(−m) = −allocate(m)`); deterministic ⇒ a golden-vectored conformance surface. **Doc correction:** `allocate/split` removed from the "takes a `RoundingMode`" op list — it takes an `AllocationRule`. *(Origin: a fixed-point 4dp percentage bite — money-splitting is the case where `Rational` is the *wrong* fix and a conserving `allocate` is the right one.)*
- **2026-07-17 · `Percentage` = `Rational`, apply-only; new `Rational` primitive** → `Percentage`/`TaxRate` are backed by a **`Rational`** — an exact `(num, den)` big-integer fraction — not `FixedDecimal`. **Why:** a fixed-point fraction *materialises* `1/3` as `0.333333` and loses it; the drift (`1/3 · 3 = 0.999999 ≠ 1`) is baked in at construction and no comparison rule can undo it without lying about some *other* pair (epsilon does — breaks transitivity, already rejected at `:comparison-exact`). A `Rational` never materialises the recurrence, so it preserves **fraction identity** — one capability that delivers three things at once: exact `1/3 · 3 == 1`, `0.999… == 1`, and **recurrence-detection** (a denominator fact: strip 2s/5s, remainder 1 ⇒ terminates). **No new dependency** — `bigint`/`BigInteger` are already in for intermediates; "no bignum lib" (`FixedDecimal`) meant *decimal* bignums, not big integers. **No new conformance surface** — `Money × Rational` is `minor × num` then divide-with-rounding by `den`, the *same* shared function with `den` in place of `10^scale`. **Apply-only in `f8n`** (`Money × Percentage → Money`); `Percentage × Percentage` compounding grows denominators and lives in `yield` on `Rational` directly — resolves the apply-only follow-up. **Serialisation = one canonical string `"num/den"`** (gcd-reduced, `den>0`, sign on `num`, zero `0/1`, integers keep `/1` ⇒ canonical ⇒ equal values have identical strings, wire/DB equality = string equality). **Not two ints:** `num`/`den` are big integers, so a JSON number (float64, loses >2⁵³) and an `int64` DB column both fail on `yield`'s compounded denominators — string-typed regardless; and a rational is one atomic value, so one token beats two fields kept in sync. `ExchangeRate` **stays `FixedDecimal`** (market value at a consumer-chosen scale, never a clean fraction). *(Origin: the `1/3·3==1` question — `0.999…=1` is true of the infinite object, but `f8n` never holds it; fixed-point holds a terminating approximation that genuinely isn't 1, so the fix is to not materialise, i.e. carry the fraction.)*

## Relationship to l10n
`f8n` is the base; `l10n` sits on top. The money/date/percentage **formatters** in `l10n` consume `f8n`'s primitives, but formatting (locale-specific presentation) lives in `l10n`, not here. Keep the boundary crisp: `f8n` = identity + math + canonical data; `l10n` = presentation. **The corollary, which is the easy one to breach: `l10n` does no arithmetic.** Deriving `12.34` from `1234` minor units looks like formatting and is not — it is scaled-integer division, so it belongs here and `l10n` receives the finished digits. Anything on the presentation side that starts computing a value is the seam slipping. See `../l10n/DESIGN.md`.
