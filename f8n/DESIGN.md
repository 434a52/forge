# f8n — design

Standalone, broadly-reusable **domain primitives — Country, Currency, Money** — generated cross-language (C# + TS) from canonical data. The base layer the rest of the stack sits on (`l10n`, `doppel`, `yield` all consume it). Personal open-source (destined).

> **Name:** **`f8n`** — numeronym for *foundation* (f + 8 + n), matching the house style (`l10n`, `a11y`). Also sidesteps the Zurb Foundation (CSS framework) collision. Quicker to type; reads as a family with the rest of the stack.

> ⚠️ **UNRESOLVED — licence conflict in the data sourcing (blocks the data pipeline; decide before the walking skeleton bakes it).** Debian **`iso-codes` is LGPL-2.1** (pycountry is LGPL *because* it embeds it). Embedding iso-codes-derived tables as **generated code inside an MIT `f8n` is murky** — and the EU **sui-generis database right** weakens the "facts aren't copyrightable" defence. `doppel/DESIGN.md` did this analysis (CC0-over-CC-BY-SA); this doc never did.
> **Likely resolution: go CLDR-only** (Unicode licence, permissive) — CLDR already carries territory/currency codes, official names, and everything relational the split below routes through it, so `iso-codes` is only doing "code lists + official names" that CLDR also has. Drop `iso-codes`, or demote it to a **non-redistributed** build-time cross-check.
> *Time-sensitive: this is training-data knowledge about licences — **verify current licence texts** before wiring the pipeline.* See the **Data sources split** decision + the **Source pipeline** agenda item.

## North star (every decision serves these)
1. **Cross-language conformance** — C# and TS produce **identical** output: *provable by construction* for the integer core (add/sub/mul-by-int on scaled integers), and **golden-vector-verified** for the one divergent surface (`divide-with-rounding`). Same DNA as `l10n` (verified against comprehensive vectors — the guarantee is the coverage, not all-inputs).
2. **Canonical data, kept current** — sourced from authoritative places (CLDR, Debian `iso-codes`); a cron rebuild raises a PR on any upstream diff (data current, changes reviewed — the machine-generates → human-gate signature).
3. **Codegen'd data, hand-maintained behaviour** — `c5n` generates the canonical **data** (currency/country reference tables from CLDR/iso-codes) into a **typed structure**; the **behaviour** (money math, parsing, resolution) lives in **hand-maintained classes** that consume that structure, written once per language and verified identical by golden vectors. Typed throughout → wrong usage is a compile error. *(The c5n split, applied here: generate the data + typed surface; hand-write the algorithm — see `../c5n/DESIGN.md` → Generation model. Behaviour is NOT codegen'd.)*
4. **Useful beyond localisation** — a general-purpose primitives library, not an `l10n` internal.

## Scope boundary — what `f8n` stores vs what it only types
The sharpest recurring line in the design:

> **`f8n` stores canonical *identity / reference* data** (ISO country & currency, CLDR formatting facts) — single-sourced, stable, fit for the cron→PR pipeline.
> **It does *not* store market- or policy-driven *values*** (FX rates, tax schedules) — for those it owns the **type + behaviour**, and the values are **supplied from outside**.

FX (fast, market) and tax (policy, jurisdiction-specific, no canonical commodity-level source) both fall on the "type here, values external" side. Owning those datasets would blow scope, lack a canonical source, go stale, and — for tax — create a **compliance liability** (wrong rate → mis-charged VAT). See the `TaxRate` and `ExchangeRate` decisions.

## The primitives
Core set: **`FixedDecimal` · `Money` · `Country` · `Currency` · `Locale` · `PhoneNumber` · `IsoDate`/`IsoTime`/`IsoDateTime`** + the rate types below. **Domain taxonomies** (industry codes like SIC, credit-rating scales like Fitch, …) are **out of scope** — they belong in the consuming/domain layer and are *generated by* f8n's codegen + `EffectiveDated` tooling, **not shipped as f8n types** (that's how a shared library's type surface multiplies). See `data-lookups.md`.

**Numeric**
- **FixedDecimal** — a general **fixed-point decimal carrying its own scale**; exact, no bignum lib. The substrate `Money` and the rate types build on, **and the explicit precision / calc space**: FX intermediates, accrual ledgers, unit prices (e.g. fuel £1.459/L) — anywhere precision above a currency's dp is wanted, at a scale the *consumer* chooses. Home of the shared C#/TS fixed-point arithmetic + **divide-with-rounding** conformance surface. (The "some kind of Decimal" wanted for `Rate` at the very start; answers "does `Decimal` carry a per-instance scale?" → yes.)
- **Money** — value + currency, an **exact integer count of the currency's minor units** (GBP 2 dp, JPY 0, BHD 3). Add/subtract are exact; precision-losing ops (× rate, ÷, allocate) take a `RoundingMode` → `Money` at currency dp. **No hidden working precision** — need sub-currency precision (FX processing, accrual)? Enter `FixedDecimal` explicitly, work, convert back to `Money` with a mode. Behaviour: arithmetic, comparison, rounding, and **invariant (culture-free) serialization only** — all *locale-aware* format/parse is `l10n`, imported (tree-shaking; see `../l10n/DESIGN.md`).

**Identity** (ISO code lists via `iso-codes`; relational/structural attributes via CLDR — see Data sources)
- **Country** — ISO 3166: **alpha-3 (id / table key)** / alpha-2 / numeric; official name; **calling code** (E.164); **default currency** + **capital's civil timezone** (a single well-defined representative zone, CLDR). *Defer:* subdivisions (3166-2) **+ per-subdivision timezones**, flags, containment.
- **Currency** — ISO 4217: alpha-3 (id) / numeric; name; **default symbol** (canonical only — locale-specific presentation stays `l10n`'s); **minor-units / exponent** + **cash-rounding** (CLDR supplemental — CHF 0.05). *Defer:* historical/withdrawn.
- **Locale** — BCP 47 tag: parse / validate / **canonicalise** (likelySubtags) / match; decompose to language·script·region. **Identity only** — formatting / plurals / display-names are `l10n`. (Platform `CultureInfo`/`Intl` aren't consistent across OS/ICU versions, so baking locale identity is a conformance win, not duplication. Locale is easily mistaken for an `l10n` concern; it isn't — matching and canonicalisation have no presentation in them.)
- **PhoneNumber** — simple wire-transport pair `{ number: string, country: alpha-3 }`; E.164 = `+` + the country's calling code + number. Simple input parsing (not libphonenumber-scale). **Stores the country explicitly** because calling-code→country is 1:many (`+1` = US/CA/NANP, `+44` = UK + crown dependencies) — country→calling-code is the safe 1:1 direction.

**Temporal** — a **TS-side polyfill** bringing TS up to C#'s native value types (C# has these already; `c5n`'s type-map binds one logical type → native C# / provided TS):
- **IsoDate** ↔ `DateOnly` — **civil, zone-less date** (the tax/policy temporal kind; see `data-lookups.md`).
- **IsoTime** ↔ `TimeOnly` — wall-clock time of day.
- **IsoDateTime** ↔ `DateTimeOffset` — an **instant, always offset/`Z`-bearing**. **Never a naked local datetime** (`DateTimeKind.Unspecified` / a zone-guessing JS `Date`) — that ambiguous middle re-introduces the BST-boundary bug. Three types (civil date / wall time / instant), *pointedly not* a floating-local-datetime.

Common characteristics: immutable value types; **ISO-8601 on the wire, parsed by strict regex over a *defined subset*** (own it — platform parsers are lenient/culture-sensitive/engine-inconsistent; strict regex = conformant-by-construction, both langs accept/reject identically). Helpers added as needed (representation-first); any *math* helper (add-days, diff) is a conformance surface → fixture it. **Open:** pin the accepted ISO subset (offset forms `Z`/`±HH:MM`, fractional-seconds precision; reject week/ordinal dates).

Rate-like values: **distinct nominal domain types over a shared internal fixed-point fraction** (the type says what the thing *is*; the arithmetic/conformance machinery is shared once). `%` / bp are constructors + formatters (display → `l10n`), never types.
- **Percentage** — plain **dimensionless proportion** (a `FixedDecimal` fraction at a scale suited to its use). VAT, fee, discount, generic `Money × p → Money`, same currency. (4.52% → `0.0452`.)
- **InterestRate** — a `Percentage` **+ a time basis** (p.a.). *Cannot* be applied to Money until a period turns it into a factor — carries a real time dimension, hence its own type.
- **ExchangeRate** — a ratio **+ a `(from, to)` currency pair**; the *only* rate that changes currency, via `Money(A).convert(rate) → Money(B)`. Takes a **directly-provided rate (first-class)**; preloading a dated series is optional. `f8n` owns type + behaviour; *values* come from outside (market data).
- **TaxRate** — a `Percentage` **+ `(jurisdiction, tax-type, category)`** — e.g. `(GBR, VAT, standard) = 20%`. Scoped to **transaction taxes** (rate × amount: VAT/sales/GST/withholding), **not** an income/corp/CGT/payroll *engine*. `Money.taxOf(rate)` takes a rate directly (first-class); the dated schedule is optional. `f8n` owns type + apply-behaviour (net↔gross); *values* external; ships only a **static, non-authoritative dated sample**. Key on **`Country`** for now, designed to widen to a `Jurisdiction` hierarchy (US sales tax is sub-national + stacking) later.

**Rates are dated facts, not scalars.** The commonest money bug in the wild is a hardcoded `0.20` — correct the year it was written, silently wrong when the rate moves (UK VAT: 17.5% → 15% in 2008 → 17.5% in 2010 → 20% from 2011-01-04). So every rate value is `(…, validFrom, validTo?)`; `Money` is timeless, **rates are temporal**. Consequences:
  - **Generalises across rate types** — FX is point-in-time, interest rates change, tax bands get reclassified. Dating is a *shared* concern, not a `TaxRate` special case.
  - **The date lives in *resolution*, not the math** — schedule + date → resolved `Percentage`; then `Money × Percentage` is date-free. Temporal logic stays in one place (the lookup).
  - **Valid-time only, not bitemporal** — effective dates yes; "when we learned it" (knowledge time) is a complexity sink, skip unless `yield` forces it.

## Data & lookups → `data-lookups.md`
The data side — what `f8n` ships vs types, the `EffectiveDated<Key, Value>` lookup, consumer-data codegen, and the temporal model — lives in **`data-lookups.md`**. In brief:
- **Building blocks, not an engine** — `f8n` ships canonical identity (ISO country/currency); rate *values* are **supplied** via the `EffectiveDated` lookup (dependency inversion). Direct value first-class; lookup optional.
- **Consumer data → typed accessors** — a build tool turns consumer YAML into **named constants that are `f8n` types** (one-way dep, "ref sticks", value-based API holds no ref).
- **Timeless value vs named binding** — the series attaches to the *name*; all named rates generate as a **uniform `EffectiveDated` series** (constants normalised in authoring only).
- **As-of API** — `taxOf(series, date)` / `asOf(taxPoint)` basis; "current" = resolve-as-of-a-date (never newest-row); default "now" via injected clock.
- **Temporal model** — tax = civil `DateOnly` (no tz), FX = UTC instant; tz derived from the rate's jurisdiction, never a call param.

## The representation model — everything is fixed-point integers
`Money` (currency scale), `FixedDecimal` (chosen scale), and the rate types (`FixedDecimal`-backed) are **all scaled integers**, so add/subtract/multiply-by-integer are **identical by construction** across C# and TS.

**`Money` is exact at its currency's dp — no hidden working precision.** A `Money` is an integer count of minor units at the currency scale (GBP 2, JPY 0, BHD 3). Add/subtract never lose anything. **Precision is opt-in, not global:** where a calculation needs more (FX processing, accrual, triangulation-style multi-hop), you *explicitly* enter `FixedDecimal` at a scale you choose, do the work, and convert back to `Money` with a rounding mode. This replaces the earlier "6 dp everywhere, settle at the boundary" model — that was an over-generalised FX/euro-conversion habit (rates were 6 sig-fig, triangulation mandated ≥3 dp intermediates); the precision belongs to the *FX/calc context*, not to every `Money`.

The precision-losing operations — **× rate, ÷, allocate/split** — take a `RoundingMode` and land back on the target currency's dp:
```
result_minor = round( money_minor × rate_scaled / 10^(rate_scale) , mode )   // → currency dp
```
Integer multiply, then integer divide-with-rounding. **The whole cross-language conformance claim collapses onto one shared function: divide-with-rounding.** That function is what the golden-vector harness targets; everything else can't diverge.

**Intermediate precision:** `money_minor × rate_scaled` overflows `int64` for large amounts, so intermediates use **arbitrary-precision integers — TS `bigint`, C# `BigInteger`** — *not* native `decimal` (whose rounding we'd otherwise have to prove matches). Both languages then run the identical integer algorithm. (`Int128` is a later perf option, not needed for v1.)

**FX precision is a consumer choice.** `ExchangeRate` is a `FixedDecimal` at a scale the consumer picks — a treasury desk wants 8 dp, a retail app 5, an accrual ledger something else. `f8n` provides the functions and lets the caller decide the right precision + rounding for their rule; it never bakes a magic scale.

**Rounding:** a `RoundingMode` enum — default **`HalfEven`** (banker's), **`HalfUp`** ("normal") also available — passed to every precision-losing op (Money × Rate, allocate/split, any divide).

- **2026-07-02 · Temporal model (civil vs instant)** → two kinds, encoded by ISO-8601 shape: **tax/policy = civil `DateOnly`** (`2011-07-01`, no `Z`; civil-to-civil compare, no tz — avoids the BST boundary-offset bug); **FX/intraday = UTC instant** (`…Z`, `DateTimeOffset`). Resolver generic over the time coordinate; never parse one value both ways. **Timezone derived from the rate's jurisdiction** (`GBR→Europe/London` via a tiny country→tz-id map from CLDR/IANA; platform does the conversion) — **never a call parameter**; only engages for instant/now inputs, not `DateOnly` tax points. Multi-tz countries = the deferred sub-national case.
- **2026-07-02 · Name** → **`f8n`** (numeronym for *foundation*); resolves the Zurb Foundation collision, matches `l10n`/`a11y` house style.

### Open follow-ups
- **`HalfUp` semantics for negatives** — half-away-from-zero (symmetric) vs half-toward-+∞? Matters only for negative Money; pick one.
- **`InterestRate` time dimension — does `f8n` own a `Duration`?** Applying an `InterestRate` needs a *period*. Either `f8n` gains a minimal `Duration`/period primitive so `rate.over(days) → Percentage`, or `InterestRate` is a *tagged marker* here and all period-application + compounding lives in `yield`. *Lean: marker here, time math in `yield` (keep time out of `f8n`).*
- **How far to push nominal tagging?** `Percentage` + `InterestRate` + `ExchangeRate` + `TaxRate` are settled as real types. Still open: also distinct `Fee` / `Discount` (semantic-only tags over `Percentage`), or leave those as plain `Percentage`?
- **Transaction-tax edges on the type** (from a tax-software domain view) — inclusive-vs-exclusive, compound stacking (PST-on-GST), per-jurisdiction rounding, exempt-vs-zero (input recovery). Which belong on `TaxRate` vs the calculation context? *(Raised; not yet worked.)*
- **Is `Percentage` apply-only or composable?** If `Percentage × Percentage` (compounding) is ever needed, a fixed-point fraction *accrues error* at whatever scale it's held — conformance still holds (both langs agree) but the value drifts from a true decimal (conformance ≠ correctness). Compounding likely lives in `yield` (in `FixedDecimal` at a chosen scale); confirm `f8n` only does `Money × Percentage → Money`.
- ~~The 6 dp working carrier — named type, or settle-immediately?~~ **Resolved (revised):** there is no working carrier — `Money` is currency-dp exact; deferred/sub-currency precision is done explicitly in `FixedDecimal` and converted back with a mode.

## Relationship to l10n
`f8n` is the base; `l10n` sits on top. The money/date/percentage **formatters** in `l10n` consume `f8n`'s primitives, but formatting (locale-specific presentation) lives in `l10n`, not here. Keep the boundary crisp: `f8n` = identity + math + canonical data; `l10n` = presentation. See `../l10n/DESIGN.md`.
